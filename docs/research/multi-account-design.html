设计与实施方案

多账号自动续火花方案

主账号保持登录不退出，在同一台服务器上并行运行多个账号，各自独立登录态、独立好友名单、独立定时与令牌，全部无人值守。方案已在你的服务器上落地并验证（账号 a、b 两个实例正在运行）。

01为什么不能"退出登录还继续跑"

"退出登录"和"后台继续运行"在逻辑上互斥。程序靠 state.json 里的 cookie 代表"你是谁"，一旦抖音侧注销，这个文件立即失效，下一次执行会直接判定"登录态已过期"。

所以本方案不采用"切换"，而是并存：每个账号一个独立进程、一份独立凭证，互不影响。主账号全程不退出。

04每日自动执行流程

阶段系统做什么失败时
1. 触发定时器按 schedule_time 触发，再随机延迟 0~N 分钟（抖动）—
2. 读配置读 config.json：好友名单、间隔、单次上限、文案池名单为空则跳过本轮
3. 起浏览器无头 Chromium 加载 state.json，打开 douyin.com/chat凭证失效→标记过期，本轮终止
4. 逐个定位在会话列表找到目标（最多重试 5 次），找不到则搜索兜底记为失败，继续下一个
5. 收件人校验确认右侧会话标题区出现目标昵称，才算切换成功校验失败→不发，记为失败
6. 发送并确认输入 → 回车 → 等输入框清空（8 秒）→ 未清空则重试 1 次仍失败→记失败
7. 节奏控制每人间隔 180~300 秒随机—
8. 落账写 runtime.json 与日志，last_run 记录成功/失败名单—
9. 失败补发本轮有失败 → 45 分钟后只补发失败者一次补发仍失败→等人工
10. 熔断检测到"操作频繁/安全验证" → 立即停止本轮需人工降频

05频率与时间编排（必须错峰）

单个账号 17 人 × 平均 4 分钟 ≈ 68 分钟。两个账号同时跑会抢 CPU 与内存，因此相邻账号的起始时间必须大于上一轮的最长结束时间 + 15 分钟。

账号发送时间抖动实际开始区间预计结束区间

b21:0020 分21:00 ~ 21:2022:08 ~ 22:28

每日频率就是"一次"。火花只要求当天有消息往来，多发无益反而增加风控暴露。不要因为"怕漏"而一天跑两轮。

好友数差异大时按行数调整：预计时长 ≈ 人数 × 4 分钟，据此倒推下一账号的起始时间。

06容量与资源上限

状态单实例内存说明
空载（等定时）约 60 MB纯 Python 服务，不含浏览器
发送中400 ~ 700 MB无头 Chromium 峰值
systemd 上限1200 MBMemoryMax 兜底，超限自动重启该实例，不拖垮整机

你的机器（2 核 4G）建议 2~3 个账号，且必须错峰。实测两个实例空载共占 593 MB，余量充足；但两个同时进入发送阶段，峰值叠加约 1.4 GB + 系统开销，仍可承受，只是 CPU 2 核会互相拖慢，导致单人耗时变长。

超过 3 个账号：先升到 2 核 8G，或按账号拆到不同机器。

07异常处理矩阵

异常检测方式系统自动行为你需要做什么
登录态过期
最常见的"故障"		 发送时判定未登录，logged_out=true 本轮立即终止，不重试（重试无效），面板状态标红 本机重新扫码该账号 → 上传新 state.json，无需重启
单条发送失败 输入框未清空 / 找不到会话 / 校验不通过 失败者进入补发队列，45 分钟后重试一次 若次日仍失败，检查该好友是否改名或被删
触发限流 页面出现"操作频繁/安全验证"关键词 立刻停止本轮（不继续硬发），rate_limited=true 把间隔调大（如 300~600 秒）、减少好友数，当天不再重试
进程崩溃 systemd 检测退出 Restart=always，15 秒后自动重启；连续崩溃会进入 failed failed 时看 journalctl -u douyin-spark@a
内存超限 超过 1200 MB 该实例被 OOM 杀掉并自动重启（会中断当轮） 减少同时运行的账号数，或降低单次上限
磁盘/日志膨胀 — 已配置 logrotate：>5MB 或每日轮转，保留 7 份并压缩 无需处理；df -h 偶尔看一眼
抖音改版 大面积失败，全是"找不到会话/元素" 无（本轮全部失败） 先 git pull 看作者是否适配；未适配需改选择器
重复发送 同一天同一好友收到两条 当前版本无日内去重，重复触发就会重复发 避免同一账号手动执行 + 定时执行撞车；建议后续补去重逻辑

10三个风险，必须在扩大账号数前想清楚

1. 同一 IP 跑多个抖音账号 = 关联风险（最重要）。抖音对同出口 IP 的多账号操作很敏感，一旦判定关联，可能一封一串。主号 + 自己的小号风险尚可接受；帮别人跑，风险会牵连到对方的账号。

2. 他人账号的授权与凭据责任。state.json 等于对方账号的钥匙。帮朋友跑最好有明确同意；一旦泄露，责任在你。这也是我不建议把它做成收费 SaaS 的核心理由。

3. 登录态仍会过期。每个账号每隔几天到几周就要有人重新扫一次码，账号越多，这个人工成本越高。这是所有方案都绕不开的硬成本，不是靠架构能解决的。

本方案已在你当前服务器（Ubuntu 24.04 / 2核4G）落地：账号 a 沿用原数据并迁移至统一结构，账号 b 已创建为空槽位等待扫码。代码改动仅 core/config.py 一处（数据目录支持环境变量，不设置时行为不变），原文件已备份为 config.py.bak-single。
提醒：自动化发私信违反抖音社区公约，多账号同 IP 运行会放大关联风险，请自行评估并控制规模。
